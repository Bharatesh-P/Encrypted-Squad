## Part 1: Architecture Diagram, On-Disk Byte Layout, Write Ordering & Recovery Flow

![KVDB Architecture Diagram and On-Disk Byte Layout](diagrams/architecture.svg)

### Component & Byte-Format Summary (Matching Code in `include/kvdb/` and `src/`)

1. **Authoritative Single-File Log (`<path>`):**
   * **12-Byte File Header (`offset 0..11`):** `magic = "KVDB"` (`4B 56 44 42`), `version = 1` (2B LE), `flags = 0` (2B LE), `header_crc32` (4B LE over bytes `0..7`).
   * **32-Byte Record Header (`offset 12..EOF`):** `record_magic = 0xAA55` (2B LE), `record_type` (1B: `0x01` PUT, `0x02` DEL, `0x03` COMMIT), `flags` (1B: `0x00` standalone, `0x01` `BATCH_MEMBER`), `txn_id` (8B LE), `op_index` (4B LE), `op_count` (4B LE), `key_len` (4B LE), `value_len` (4B LE), `record_crc32` (4B LE over header bytes `0..27` + key + value).
   * **Variable Payload:** `key_len` bytes (`1..1,024`) followed by `value_len` bytes (`0..1,000,000` for PUT, `0` for DEL, `4` for `batch_crc32` on COMMIT).
2. **In-Memory Value-Offset Index (`include/kvdb/index.hpp`):**
   * `std::unordered_map<std::string, IndexEntry>` where `IndexEntry` stores `{ uint64_t value_offset; uint32_t value_len; }`. Value payloads remain on disk, keeping memory usage low and `open()` fast.
3. **Concurrency Control (`src/engine.cpp`):**
   * Global `std::shared_mutex mutex_`: `Database::get()` and `Database::dump()` acquire `std::shared_lock`; `Database::put()`, `Database::del()`, `Database::batch()`, `Database::compact()`, and `Database::close()` acquire `std::unique_lock`.
4. **Numbered Write Ordering (`src/engine.cpp`):**
   * **Single `PUT`/`DEL`:** `(1)` Acquire `unique_lock` & check `append_offset_ + rec_size <= max_bytes_` (auto-compacting if `dead_records_ > 0`) $\rightarrow$ `(2)` `file_.write_all_at()` $\rightarrow$ `(3)` `file_.sync()` (`fsync` / `FlushFileBuffers`) $\rightarrow$ `(4)` Update `index_` and `append_offset_` $\rightarrow$ `(5)` Release lock and emit `ACK <op-id>`.
   * **Two-Phase `BATCH`:** `(1)` Acquire `unique_lock` & check `append_offset_ + total_batch_bytes <= max_bytes_` $\rightarrow$ `(2)` Append all `op_count` member records with `flags = kFlagBatchMember` $\rightarrow$ `(3)` First `file_.sync()` $\rightarrow$ `(4)` Append 36-byte `COMMIT` marker with aggregate `batch_crc32` $\rightarrow$ `(5)` Second `file_.sync()` $\rightarrow$ `(6)` Apply all `ops` in `0..op_count-1` order to `index_` $\rightarrow$ `(7)` Release lock and emit `ACK <op-id>`.

## Part 3: The Three Guarantees, Argued

### 1. Durability: Why Once `ACK` Is Sent, the Data Survives
In `Database::put()` and `Database::del()` (`src/engine.cpp`), while holding `std::unique_lock<std::shared_mutex>`, the engine serializes the 32-byte header (including `record_crc32`) and payload, writes all bytes to the log via positional `pwrite()` (POSIX) or `WriteFile()` with `OVERLAPPED` offsets (Windows), and immediately invokes `fsync(fd)` (POSIX) or `FlushFileBuffers(handle)` (Windows). For `Database::batch()`, the engine appends all member records, calls `fsync()` / `FlushFileBuffers()`, appends the 36-byte `COMMIT` marker containing `batch_crc32`, and calls `fsync()` / `FlushFileBuffers()` a second time. Only after the final `fsync()` / `FlushFileBuffers()` syscall returns success does the engine update the in-memory `index_`, assign a `commit_seq_`, and return `Status::Ok()` to `main_kvdb.cpp`, which then writes `ACK <op-id>` to `stdout`. Because the OS and disk honor `fsync()` / `FlushFileBuffers()`, every acknowledged operation is physically on disk before `ACK` is emitted and cannot be lost by a subsequent `kill -9` / `TerminateProcess`.

### 2. Atomicity: Why a Batch Is Never Half Visible
A batch of `op_count` operations shares a single `std::unique_lock<std::shared_mutex>` acquisition in `Database::batch()` (`src/engine.cpp`), preventing any concurrent `get()` or `dump()` (which require `std::shared_lock`) from reading the in-memory `index_` until all `op_count` operations have been applied to `index_` after the second `fsync()`. On disk, every batch member record has `flags = kFlagBatchMember (0x01)`. During crash recovery in `recover_database()` (`src/recovery.cpp`), records with `kFlagBatchMember` are buffered in a local `pending_ops` vector and are never inserted into `out_index` until a `RecordType::COMMIT` record (`0x03`) with a valid `record_crc32`, matching `txn_id`, matching `op_count`, and matching aggregate `batch_crc32` over all member bytes is verified. Because the `COMMIT` marker is written only after the first `fsync()` of all member records completes, a `COMMIT` marker on disk implies all member records are on disk; if a crash occurs before the `COMMIT` marker is completely written, `recover_database()` calls `ftruncate()` / `SetEndOfFile()` to roll the file back to `batch_start_off`, erasing all members of the uncommitted batch.

### 3. Recoverability: Why `open()` Always Succeeds on Any File Produced by Our Database
Our authoritative state is a single append-only file (`<path>`) where regular mutations only append bytes at `append_offset_`, never overwriting existing committed records in place. If the process is killed during initial file creation when `<path>` is shorter than 12 bytes, `recover_database()` truncates `<path>` to `0`, writes a valid 12-byte `KVDB` header, and calls `fsync()`. If killed mid-append of a single record or batch, the damage is strictly confined to the tail of the file, which `recover_database()` detects via length bounds (`file_size - offset < total_rec_len`) or `record_crc32` / `batch_crc32` verification and repairs via `ftruncate()` / `SetEndOfFile()` to `rollback_target` (`record_start` or `batch_start_off`) followed by `fsync()`. Because `ftruncate()` to a deterministic transaction boundary is idempotent, killing `open()` during recovery and running `open()` again repeats the exact same scan and truncation. Finally, `compact_database()` (`src/compaction.cpp`) writes and calls `fsync()` on `<path>.tmp` before invoking atomic `rename()` + parent-directory `fsync()` (POSIX) or `MoveFileExW(..., MOVEFILE_REPLACE_EXISTING | MOVEFILE_WRITE_THROUGH)` (Windows), ensuring `<path>` always points to either the complete old log or the complete compacted log, while `recover_database()` removes any leftover `<path>.tmp` file.
